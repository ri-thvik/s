1. DOCKER – MULTI-CONTAINER APPLICATION
--------------------------------------------------------------------------------

TASK 1.1: PULL MYSQL AND WORDPRESS IMAGES
-------------------------------------------
$ docker pull mysql:8.0
$ docker pull wordpress:latest
$ docker images
# Expected: REPOSITORY TAG IMAGE ID SIZE
# mysql 8.0 ~500MB, wordpress latest ~570MB

TASK 1.2: CREATE CUSTOM DOCKER NETWORK
----------------------------------------
$ docker network create library-network
$ docker network ls
# Expected: NETWORK ID NAME DRIVER SCOPE

TASK 1.3: RUN MYSQL CONTAINER WITH PERSISTENCE
----------------------------------------------
$ docker run -d --name library-mysql \
  --network library-network \
  -e MYSQL_ROOT_PASSWORD=Root@12345 \
  -v mysql-data:/var/lib/mysql \
  --restart unless-stopped mysql:8.0

$ docker ps
# Expected: CONTAINER ID IMAGE COMMAND STATUS PORTS NAMES
# library-mysql mysql:8.0 Up <seconds> 3306/tcp library-mysql

TASK 1.4: RUN WORDPRESS CONTAINER LINKED TO MYSQL
---------------------------------------------------
$ docker run -d --name library-wordpress \
  --network library-network \
  -p 8080:80 \
  -e WORDPRESS_DB_HOST=library-mysql:3306 \
  -e WORDPRESS_DB_USER=root \
  -e WORDPRESS_DB_PASSWORD=Root@12345 \
  -e WORDPRESS_DB_NAME=librarydb \
  --restart unless-stopped wordpress:latest

$ docker ps
# Expected: PORTS: 0.0.0.0:8080->80/tcp

TASK 1.5: ACCESS WORDPRESS IN BROWSER
----------------------------------------
$ # Open browser and visit:
$ http://localhost:8080
# Expected: WordPress language selection page loads
# Select language and continue - database already configured

TASK 1.6: DEMONSTRATE CONTAINER RECOVERY AND DATA PERSISTENCE
--------------------------------------------------------------
$ # Stop MySQL container (simulate crash)
$ docker stop library-mysql
$ # Start MySQL container again (simulate recovery)
$ docker start library-mysql
$ # Verify data persistence
$ docker exec library-mysql mysql -uroot -pRoot@12345 -e "SHOW DATABASES;"
$ # If volume removed, data LOST; with -v mysql-data, data PRESERVED

================================================================================
DOCKER SCENARIO QUESTIONS (MASTER THESE)
--------------------------------------------------------------------------------
Q: What happens if MySQL container crashes while WordPress is running?
A: WordPress shows database connection errors, pages won't load. MySQL needs restart.

Q: How can database information be recovered after container deletion?
A: If persistent volumes were used (-v mysql-data), data survives. Restart new MySQL 
  container pointing to same volume.

Q: Why is a custom Docker network required?
A: Allows containers to discover each other by name instead of IP addresses. 
  Provides isolation from other Docker containers.

Q: How would you prevent unauthorized access to MySQL?
A: Strong passwords, bind to specific IPs, Docker secrets, MySQL user privileges.

Q: How would you deploy five department websites using Docker?
A: 5 WordPress containers, each with own volume, same network, one MySQL instance, 
  different port mappings (8080, 8081, 8082, etc.).

================================================================================
JENKINS SCENARIO QUESTIONS (MASTER THESE)
--------------------------------------------------------------------------------
Q: How does Jenkins identify compilation errors?
A: Errors appear in Console Output with ERROR prefix, showing file path and line 
  number. Build fails if any compilation errors exist.

Q: What if compilation succeeds but tests fail?
A: Depends on Maven goal: mvn compile → build succeeds. mvn test → build fails. 
  Can set failTestsWithNoTests=false.

Q: Why Maven instead of manual JAR downloads?
A: Dependency management via pom.xml, handles transitive dependencies, reproducible 
  builds, uses Central Maven Repository.

Q: How to build only specific Git branch?
A: Branches to build → */main or use wildcard *. Or configure Multibranch Pipeline.

Q: Difference between CI and CD?
A: CI (Continuous Integration): Automated build + test on every commit. 
  CD (Continuous Deployment): Automated deployment to prod/staging after CI passes.

3. KUBERNETES – CONTAINER DEPLOYMENT AND AUTO SCALING
--------------------------------------------------------------------------------

TASK 3.1: START MINIKUBE CLUSTER
---------------------------------
$ minikube start
$ minikube status
# Expected: minikube: Running, cluster: Running, kubectl: Correctly configured

TASK 3.2: CREATE DEPLOYMENT WITH TWO REPLICAS
-----------------------------------------------
$ kubectl create deployment library-app --image=wordpress:latest --replicas=2
$ kubectl get deployment library-app
# Expected: NAME READY UP-TO-DATE AVAILABLE AGE
# library-app 2/2 2 2 <timestamp>

TASK 3.3: EXPOSE APPLICATION USING KUBERNETES SERVICE
------------------------------------------------------
$ kubectl expose deployment library-app --type=NodePort --port=80
$ kubectl get service library-app
# Expected: PORT(S) column: 30000/80/tcp (30000 = NodePort, varies each time)

TASK 3.4: SCALE DEPLOYMENT FROM 2 TO 5 REPLICAS
--------------------------------------------------
$ kubectl scale deployment library-app --replicas=5
$ kubectl get deployment library-app
# Expected: READY column should show 5/5 (was 2/2)

TASK 3.5: DEMONSTRATE AUTOMATIC POD RECRUPTION AFTER FAILURE
-------------------------------------------------------------
$ kubectl get pods -o wide
$ # Note pod names (e.g., library-app-5d6f9b7d4c-pxxxy)
$ kubectl delete pod library-app-5d6f9b7d4c-XXXXX
$ kubectl get pods -o wide
# Expected: New pod appears and starts Running automatically

TASK 3.6: PERFORM ROLLING UPDATE AND ROLLBACK
-----------------------------------------------
$ # 6a: Rolling Update
$ kubectl set image deployment/library-app library-app=wordpress:latest
$ kubectl rollout status deployment/library-app

$ # 6b: Rollback to Previous Version
$ kubectl rollout undo deployment/library-app
$ kubectl rollout status deployment/library-app

$ # Check revision history
$ kubectl rollout history deployment/library-app

================================================================================
KUBERNETES SCENARIO QUESTIONS (MASTER THESE)
--------------------------------------------------------------------------------
Q: What happens when one pod crashes?
A: Kubernetes Deployment controller notices desired state not met. Creates new pod 
  automatically via ReplicaSet. Pod goes through Pending → ContainerCreating → Running.

Q: How does Kubernetes maintain desired replicas?
A: Deployment controller constantly compares current state vs desired state. If fewer 
  pods running, creates new ones. Uses ReplicaSet to manage pods.

Q: Manual vs auto scaling?
A: Manual: kubectl scale deployment name --replicas=N. Auto: Horizontal Pod 
  Autoscaler (HPA) based on CPU/memory metrics.

Q: Why Kubernetes Service required?
A: Provides stable networking endpoint. Pod IPs change when pods recreated, but 
  Service IP stays constant. Enables reliable communication.

Q: Recover from failed application update?
A: kubectl rollout undo deployment/<name> rolls back to last good version. 
  kubectl rollout history shows revision history.

================================================================================
NAGIOS SCENARIO QUESTIONS (MASTER THESE)
--------------------------------------------------------------------------------
Q: How does Nagios identify high CPU utilization?
A: Via check commands (e.g., check_cpu plugin). Returns WARNING if above threshold, 
  CRITICAL if higher.

Q: Difference between WARNING and CRITICAL?
A: WARNING: Problem detected but might recover (ORANGE). CRITICAL: Serious problem, 
  definitely degraded (RED).

Q: Identify app failure when server running?
A: Service checks (HTTP, port, custom scripts) detect app-level failures independent 
  of server health.

Q: Nagios monitoring server fails?
A: Monitoring stops. No alerts until restarted. Redundant/multiple Nagios instances 
  recommended.

Q: Identify downtime cause (Tomcat, MySQL, networking)?
A: Check each: 1) Web app access (Tomcat), 2) DB connection (MySQL), 3) Network 
  connectivity, ping, ports.

5. AWS – CLOUD DEPLOYMENT USING EC2
--------------------------------------------------------------------------------

TASK 5.1: LAUNCH EC2 INSTANCE
------------------------------
$ # AWS Console → Launch Instance
$ # AMI: Amazon Linux 2023 or Ubuntu Server
$ # Instance type: t2.micro (free tier) or suitable
$ # Key pair: Create new .pem file, keep secure
$ # Security Group: Configure rules (see below)
$ # Note: Public IPv4 DNS or IP (required for browser access)

TASK 5.2: CONFIGURE SECURITY GROUPS
--------------------------------------
$ # INBOUND RULES:
$ # 1. SSH (port 22) - Your IP only (RESTRICTED!)
$ #   Type: SSH, Protocol: TCP, Port: 22, Source: 203.0.113.0/32 (your IP)

$ # 2. HTTP (port 80) - Anyone (browser access)
$ #   Type: HTTP, Protocol: TCP, Port: 80, Source: 0.0.0.0/0

$ # 3. Custom TCP (port 8080) - If app runs on 8080
$ #   Type: Custom TCP, Protocol: TCP, Port: 8080, Source: 0.0.0.0/0

$ # OUTBOUND RULES: Allow All Outbound (default)
$ #   Type: All Traffic, Protocol: All, Port: All, Destination: 0.0.0.0/0

$ # ⚠️ NEVER open SSH (port 22) to 0.0.0.0/0

TASK 5.3: INSTALL TOMCAT AND APPLICATION
------------------------------------------
$ # ssh -i your-key.pem ec2-user@<public-dns-or-ip>

$ # Install Tomcat (Amazon Linux):
$ # sudo yum install tomcat (or wget tarball, extract)

$ # Copy application:
$ # sudo mkdir -p /var/lib/tomcat/webapps/
$ # Copy WAR file to /var/lib/tomcat/webapps/

$ # Start Tomcat:
$ # sudo systemctl start tomcat

$ # Verify:
$ # sudo systemctl status tomcat

$ # Browse:
$ # http://<public-ip-or-dns>:8080/your-app

TASK 5.4: DATABASE CONNECTIVITY (RDS MYSQL)
--------------------------------------------
$ # Launch RDS MySQL Instance
$ # Engine: MySQL, Instance class: db.t2.micro (free tier)
$ # Master username: admin, Master password: (secure)

$ # Configure Security Group
$ # Allow MySQL (3306) from EC2 instance's Security Group
$ # This allows EC2 to connect to RDS

$ # Configure application connection
$ # spring.datasource.url=jdbc:mysql://<rds-endpoint>:3306/librarydb
$ # spring.datasource.username=admin
$ # spring.datasource.password=(password)

TASK 5.5: BROWSER ACCESSIBILITY
---------------------------------
$ # http://<public-ip-or-dns>:8080
$ # Verify application loads, login page appears, features work

$ # Troubleshooting If Not Accessible:
$ # 1. Check Security Group allows HTTP (80/8080)
$ # 2. Verify Tomcat running: sudo systemctl status tomcat
$ # 3. Check firewall
$ # 4. Verify Public IP/DNS is correct
$ # 5. Ensure route table associated with subnet

TASK 5.6: IMPROVE APPLICATION AVAILABILITY
-------------------------------------------
$ # Single EC2 → Problems: If instance fails, app completely down, no fault tolerance

$ # ALB + Multiple EC2 → Solutions:
$ # 1. Application Load Balancer (ALB)
$ #   - Distributes traffic across instances
$ #   - Health checks automatically
$ #   - Zero-downtime deployments

$ # 2. Multiple EC2 Instances
$ #   - 2+ instances in different AZs
$ #   - Auto Scaling Group
$ #   - If one fails, others handle traffic

$ # 3. Benefits:
$ #   - Fault tolerance (if 1 fails, others work)
$ #   - Horizontal scaling (add/remove instances)
$ #   - Zero-downtime deployments
$ #   - Better performance (distributed load)

================================================================================
AWS SCENARIO QUESTIONS (MASTER THESE)
--------------------------------------------------------------------------------
Q: What could cause EC2 application to be inaccessible through browser?
A: Security Group blocking 80/8080, Tomcat not running, firewall on instance, 
  wrong public IP, no route table association.

Q: Why should SSH access be restricted?
A: Security risk: unauthorized access, potential server compromise, brute force attacks. 
  Only allow specific IPs.

Q: What happens if Tomcat stops while EC2 is running?
A: Application becomes unavailable via browser. Need to restart Tomcat. EC2 instance 
  stays running.

Q: How can application availability be improved?
A: Multiple AZs, Load Balancer, Auto Scaling Groups, instance monitoring, 
  graceful shutdown/start.

Q: Why ALB + multiple EC2 better than single EC2?
A: Fault tolerance (if one fails, others handle traffic), horizontal scaling, 
  zero-downtime deployments, distributed load, high availability.
